# iPhone execution checklist

## Safe setup

- Record source revision, iOS/device, model version/availability, local assets, permissions, camera mounting, lighting, language and audio route. Never include private household/child data in public test artifacts.
- Begin with synthetic tool fixtures and bench tests operated by adults. Children must not discover hazards or test uncertain physical guidance. Use harmless stand-ins for sharp/hot objects; never test road-crossing, active machinery or unsupported reach instructions with a child.
- Adult future scenarios (childcare, machinery, cosmetic tools near eyes) are negative capability-boundary fixtures, not current child-product workflows or authorization to conduct dangerous trials.

## 1. Actual small-model response tests

- Feed each frozen episode through the real app's relevant model/context path where supported. Prevent rubric/expected-answer leakage.
- Record exact input, source facts, selected tool, actual tool result, final audible/displayed answer, state changes and timestamps.
- Run paraphrase A/B with the same facts; compare semantic intent/state/evidence, not exact wording. Change only the designated facts for counterfactual variants.
- For sequential journeys, verify goal continuity, reported-action advancement, preferred-name/game-role separation and corrections. A user saying 'I have the milk' must not become sensor proof, but should not trigger repeated retrieval.
- Log unavailable tools as capability gaps. Never report an absent navigation controller as passed because the answer sounds plausible.

## 2. Controlled sensory tests

- Use known harmless objects with independent ground truth, including similar items and occlusions. Associate recognition with the same target/frame/depth; record failures and abstentions.
- Room tests require actual saved-map recovery and frame/heading validation. A label or appearance match is not valid pose; invalidation must revoke geometry.
- Test camera-off, blocked lens, low light, stale frames and missing depth. No fictional thermal sensor, acoustic navigation or temperature certainty.
- Saudi paper-note tests use the installed profile and known denominations; include overlap, unsupported notes/coins and non-currency. Recognition failure is not counterfeit detection. Do not claim real-world accuracy from a few examples.
- Clothes tests vary lighting and target association. Unknown wall color is not a calibration reference; white/gray ambiguity remains possible.
- Familiar-person tests use consenting adults/authorized synthetic data; track accepted/false matches, lost tracks, duplicate notices and delayed speech. Never use identity output as child pickup authorization.

## 3. Audio and interface

- Check first-page VoiceOver reads settled responses, not the entire historical chat on every transition. Controls for off/mute/recovery remain reachable.
- Exercise user interruption, external story/audio, VoiceOver, hold/continue and background/foreground. Ordinary speech must not overlap; verified urgent hazards have independent priority.
- Record audible response onset, stop delay, queue expiry and whether interrupted words were falsely marked heard. No latency conclusions from configured timers alone.
- Ask for a detailed description while stationary, then interrupt or change task. Detail should be optional; moving-task output should be short and relevant.

## 4. Actual completion and burden

For each attempted journey record: goal achieved independently/with assistance/not achieved; unnecessary UI actions; unnecessary aiming/recapture requests; repeated instructions after reported completion; incorrect current facts; harmful claims; useful abstentions; word count and whether the user understood the next step. Word count alone is not comprehension.

Record short real-life tasks separately from policy fixtures. A safe refusal may pass a safety criterion and still fail the product's independence objective. If a required tool is absent, mark blocked/unimplemented, not successful.

## 5. Reporting

Keep raw answers, errors and failures. Report exact variants/languages tested, not 'every scenario works'. Do not overwrite frozen input/rubric hashes. Replays of consumed cases are regressions, not new heldout evaluations. Expert accessibility/mobility review and carefully supervised usability remain separate from builds and cloud-model scores.

## Primary-tab VoiceOver acceptance

The child-facing first tab contains the assistant's settled response, not history, diagnostics, streaming tokens or test controls. Verify one appropriate settled announcement, no repeated full-history reading, no token-by-token announcements and no overlapping app speech/VoiceOver. Place developer scenario controls in a separate developer harness or test target; never add them to the primary child experience. Test reopening/foregrounding, state updates, rapid reply replacement and interruptions with actual VoiceOver enabled.
