## Probe contract

The probe exists only under DEBUG and is disabled by default. Only the existing ActiveTrip and ClearRetires fixtures enable it (including ActiveTrip's reopened store). Each instrumented read/clear call gets a synthetic owner UUID, synthetic operation UUID, monotonic bounded integer index, fixed operation kind and seven fixed optional numeric timestamps. The store retains only its latest read and clear handles. Existing bounded in-flight operations retain their own handles; tests capture the exact relevant handle before waiting, so a later read cannot replace a timed-out operation's identity.

Busy rejections get a separate receipt with only an inline-delivery marker. They cannot impersonate the previously accepted operation or claim main-queue delivery. The synthetic owner IDs are generated by the probe, not read from the database. No coordinate, label, file path, observation/session/trip/database ID, payload, image, model text or error description enters the receipt.

Stages and limits:

| Marker | Actual boundary | Interpretation limit |
| --- | --- | --- |
| queued | After existing admission, immediately before enqueue | Queue interval includes earlier serial-queue jobs and scheduling; not pure scheduler delay. |
| workerStarted | First probe point inside the actual queue closure | No worker was added. |
| loadFinished | After existing load/open path returns | Clear includes its existing state reset before open. Load may have handled an error. |
| databaseReturned | Read: after `reversePage` returns; clear: after clear and following state read return | Includes preceding state/reference processing. `databaseWall` is not database CPU time or pure I/O. |
| workerFinished | After result construction, before main enqueue | Read decoding/state assembly and clear's legacy-file removal occur before this. |
| mainDelivered | First probe point in main callback, before its existing app lock and completion | Does not include that lock wait, callback body or test continuation. |
| inlineDelivered | Existing duplicate/busy return path, immediately before inline callback | This is not main-queue delivery. |

Missing load/database markers can mean an exception or short-circuit when workerFinished is present, not necessarily a hang. Missing workerStarted means this receipt has not witnessed worker entry; it does not identify which preceding operation or scheduler condition caused the delay. Times are wall-clock intervals and include preemption/probe overhead. Nothing here measures CPU utilization or proves a Simulator-specific cause.

## Failure reporting and extraction

The snapshot helper captures the current operation handle immediately after its call, then runs the original wait. It prints only after missing completion or a new XCTest failure. Reopened-state/page assertions and the queued-read/clear pair similarly retain exact handles. `WAIT_FAILURE` denotes failure context; it is not necessarily a timeout. A failed paired wait prints both read and clear receipts for comparison, **not a claim that both failed**. The optional `testRun` and its failure counter are documented XCTest APIs ([testRun](https://developer.apple.com/documentation/xctest/xctest/testrun), [failureCount](https://developer.apple.com/documentation/xctest/xctestrun/failurecount?language=objc)).
