# VTK 9.3.1 locator source review after the bounded stage-05 failure

Read-only source review, 2026-10-26. No dataset processing, VTK loading, build, benchmark, or fixture execution was performed by this reviewer. This is a new addendum; stage-05 sources, protocol, review and partial evidence remain untouched.

## Observed failure versus inferred costs

Stage-05 `run-evaluate.partial/FAILURE_RECEIPT.json` reports the sampled process-tree CPU cap: 600.1 CPU seconds, 587.2787 wall seconds, 1,437,368,320 bytes sampled peak tree RSS, child SIGKILL. No frame metrics were completed. The last log is locator-build entry after complete mesh validation. There is no build-finished checkpoint, so **the existing evidence does not identify whether construction or the first frame's queries exhausted the budget**. This is no depth-accuracy result.

The official [OBB construction source](https://github.com/Kitware/VTK/blob/v9.3.1/Filters/General/vtkOBBTree.cxx#L281-L430) calculates area-weighted triangle moments, covariance eigenvectors and projected point extents for each node. [BuildTree](https://github.com/Kitware/VTK/blob/v9.3.1/Filters/General/vtkOBBTree.cxx#L1131-L1259) repeats this per node, then may scan node cells for three candidate split planes and revisit a selected best plane. A stamped point-ID array avoids clearing all vertex marks at each node; it would be incorrect to claim such a repeated global clear. For a balanced hierarchy these are repeated cell/point passes by depth, not constant-time construction. This explains a plausible construction cost, **not a measured bottleneck**.

The [OBB nearest-hit query](https://github.com/Kitware/VTK/blob/v9.3.1/Filters/General/vtkOBBTree.cxx#L915-L980) checks candidate nodes against the full original segment, retains the smallest cell-intersection parameter, but does not shorten traversal using that best parameter. It has no full-cell visited bitmap. Whole-segment traversal is another possible cost.

## Do not substitute CellTree's nearest-hit overload unchecked

[CellTree's builder](https://github.com/Kitware/VTK/blob/v9.3.1/Common/DataModel/vtkCellTreeLocator.cxx#L442-L658) partitions axis-aligned cell bounds with bucket selection and an `nth_element` fallback, avoiding per-node covariance. However, its [nearest-hit overload](https://github.com/Kitware/VTK/blob/v9.3.1/Common/DataModel/vtkCellTreeLocator.cxx#L796-L806) breaks out of a leaf when one cell's minimum bound distance exceeds the current best hit. The leaf array is copied from partitioned input, not sorted for all six possible ray directions.

Concrete source-derived counterexample for an analytic check: a single leaf with three congruent triangles at positive ray distances **2, 4, 1**, in that input order; origin zero, ray along +Z. Hit 2 establishes the best distance; bounds at 4 trigger the break; nearest 1 is skipped. This reviewer has **not executed** that example. Existing two-plane tests do not test this ordering. Do not patch VTK or assume correctness from the API's name.

The installed-library alternative that avoids this particular early-break issue is [CellTree's all-intersections overload](https://github.com/Kitware/VTK/blob/v9.3.1/Common/DataModel/vtkCellTreeLocator.cxx#L870-L1012): supply a real `vtkGenericCell`, reusable Double `vtkPoints`, and `vtkIdList`; it intersects actual cells and sorts hits by segment parameter. Select its first returned hit, validate the segment parameter and preserve the existing inverse-transform axial-depth consistency check. Supplying no generic cell would return bounding-box hits instead of surface hits and is unacceptable. This reuses an existing library query; it does not introduce a custom search or intersection routine. Confirm all-hit behavior with the 2,4,1 ordering fixture and both triangle windings before recorded evaluation.

## Resources and alternatives

CellTree, StaticCellLocator and ModifiedBSPTree all allocate a full-cell `vector<bool>` per query that enters the root: [CellTree](https://github.com/Kitware/VTK/blob/v9.3.1/Common/DataModel/vtkCellTreeLocator.cxx#L900-L902), [Static](https://github.com/Kitware/VTK/blob/v9.3.1/Common/DataModel/vtkStaticCellLocator.cxx#L1162-L1164), [ModifiedBSP](https://github.com/Kitware/VTK/blob/v9.3.1/Filters/FlowPaths/vtkModifiedBSPTree.cxx#L598-L621). At 17,801,112 cells this is approximately 2.23 MB per query and approximately 820 GB cumulative initialization writes over 368,520 root-entering queries. This is **not simultaneous memory usage or a runtime measurement**. ModifiedBSP is not a bitmap-free answer; unlike CellTree's nearest overload it does use six directional sorted leaf lists, which add storage/construction work.

For a CellTree retry, explicitly use 64 cells per leaf, six build buckets and `CacheCellBoundsOff()`. [CellTree header](https://github.com/Kitware/VTK/blob/v9.3.1/Common/DataModel/vtkCellTreeLocator.h#L16-L25) says MaxLevel is ignored. [CellInfo](https://github.com/Kitware/VTK/blob/v9.3.1/Common/DataModel/vtkCellTreeLocator.cxx#L326-L331) already stores six doubles plus an ID per cell during construction. Disabling the separate bounds cache avoids another six-double table (854,453,376 nominal payload bytes); queries then obtain cell bounds from the existing dataset. This is a memory tradeoff, not a speed guarantee. Keep the same independent process-tree RSS watchdog.

[StaticCellLocator's nearest overload](https://github.com/Kitware/VTK/blob/v9.3.1/Common/DataModel/vtkStaticCellLocator.cxx#L1191-L1246) scans all candidates in an intersected bin, keeps the closest hit, and accepts it only in that bin before ending traversal. It does not have the same unsorted-leaf early-break issue. It is a reasonable alternative, but grid fragmentation/storage and runtime on the full scan are not established here.

No downsampling, fitting, sensor-driven clipping or metric exclusion. Freeze the new source cut; run analytic fixtures first. Persist checkpoints for mesh read/validation, locator construction start/end, first query start/end and regular completed-ray counts. Persist watchdog CPU/RSS/wall heartbeats, not only a terminal receipt. A failure still yields no completion or accuracy claim. Nothing in this source review guarantees the recorded workload will fit its budget.
