# Coordinate-provenance reconciliation (pre-publication)

## Conclusion

The projection has a documented **conditional offline coordinate chain**. It does **not** assume the original `polycam_mesh/textured.obj` is aligned with camera poses. The official warning is valid: the [MuSHRoom README](https://github.com/TUTvision/MuSHRoom#data-structure) describes that mesh as unaligned and visualization-only. A separately recorded stage37 rigid comparator fit supplies the source planner's mesh bridge. More importantly, this pixel diagnostic never reads that OBJ or its fitted vertices: it projects the saved **original-model support rays / FARO-derived hit** using the exact unchanged evaluator transform.

Thus the numerical pixel addresses and sampled original export values remain reproducible under the frozen transforms. They are **not independently verified physical correspondences** between an exact ground location or FARO triangle and a photographed surface. Image-region descriptions are only descriptions at those conditional pixel addresses. The table/caster/carpet observations do not prove occlusion, semantic triangle identity, floor support or clearance.

## Exact frames and transforms (column-vector convention)

Let `P` be the published phone-export pose coordinate frame; `F` the author FARO reference frame; `O` the raw, unaligned Polycam OBJ frame; `L_o/L_c` the original/corrected phone-derived level frames; and `q_o/q_c` their +Y-up game/model forms.

1. **Published camera poses.** Diagnostic reads each `C_i = transformations.json.frames[i].transform_matrix`, camera-to-`P` in OpenGL convention. Actual selected basenames are00024,00119,00248; their complete matrices and intrinsic fields are exactly numerically equal to matching entries in original `transformations_colmap.json`. This verifies only these selected entries; it does not infer provenance from the COLMAP filename. The author's [supplement §1.2](https://arxiv.org/html/2311.02778v3) explains unsuccessful COLMAP estimation for Koivu/activity and use of Polycam capture loops. No corrected/locally refined per-frame pose was substituted here.
2. **Phone-to-FARO registration.** `A = icp_iphone.json.gt_transformation`. Retained original Zenodo10222321 metadata explicitly associates `icp_iphone` with the pose file named `transformation_colmap.json` and reference mesh/point cloud. The actual author renderer uses plural `transformations_colmap.json`, applies `A^-1` to the FARO mesh, and renders with those camera poses. This association/direction is independently retained in stage04 `PAIRED_REFERENCE_FEASIBILITY.md` and its pinned renderer source digest. The [official data layout](https://github.com/TUTvision/MuSHRoom#data-structure) names this as the iPhone aligned transformation. The exact selected pose equality above is the bridge permitting use of original `transformations.json` for this local diagnostic.
3. **Original model frame.** The existing allowlisted metadata contains `R_o,t_o` from original `koivu_5cm_v2_pipeline2_out.npz` (source SHA256 `a2fc5c13f86bf7033131347fd9b6d61db23ab716d12d668a3d969b9e87dbf48d`). Local `pipeline.py:load_frames/lidar_samples/level_frame` reads `transformations.json`, unprojects published depth into `P`, and defines `L_o = R_o P + t_o`. The corrected metadata comes from the separate floorfix output (source SHA256 `ac63b5219a61094d754b6303d40b7f9dc0905a2abe446b6070bab94458c592d7`). These source NPZs were not reloaded or reconstructed in this diagnostic; the exact allowlisted R/t and saved evaluator-transform hash were verified instead.
4. **Basis change.** `B = [[1,0,0],[0,0,-1],[0,1,0]]` maps game/model coordinates to level coordinates: `L_o = B q_o = [q_x,-q_z,q_y]`. Therefore `N(q_o) = R_o^T (B q_o - t_o)` maps model→`P`. No OctoMap +0.025m grid-centre offset is added: the unchanged evaluator explicitly uses the plane-level frame before that offset.
5. **Evaluator transform.** Stage84 `physics_primitives.transform` builds `M = A N`, mapping model→FARO. The diagnostic reuses that unchanged function, checks its full matrix-byte SHA256 against the saved support-ray receipt, and computes `N = A^-1 M`. This is cancellation of the existing transform, not a fit. No raw OBJ transform occurs here.
6. **Pixel projection.** For a saved model point `q`, camera point is `c_i = C_i^-1 N q`. With `d=-c_z`, screen coordinates are `u=fx*c_x/d+cx`, `v=-fy*c_y/d+cy`; nearest stored address is `(floor(u),floor(v))`, consistent with the existing half-pixel rays `(column+0.5,row+0.5)`. For the actual FARO hit `f=Mq`, this is exactly `c_i=C_i^-1 A^-1 f`. For missing rays there is no `f`; modelY=0 is only an indexing location on the saved model query, not an asserted floor hit.

## Where the unaligned Polycam OBJ enters—and where it does not

The **source planner**, before any pixel inspection, uses the historical stage37 fit `Q,s` to place raw OBJ vertices in corrected level coordinates: `L_c=Q O+s`. That fit is `CANDIDATE_RIGID_TRANSFORM.npz` SHA256 `4085c76c14e1e97acd939a302daf1a9cd1f258b86d97e8e08ea6e6e9aae8da8f`; scale is fixed1. Stage37 `register.py` fits against a phone-derived Open3D TSDF in the corrected level frame—not FARO—and its protocol forbids reference/route-based fitting. Stage84 `pair_planner.py` builds the source mesh in game coordinates `q_c=B^T L_c`. It converts returned paths to the original model frame:

`q_o = B^T [ R_o R_c^T (B q_c - t_c) + t_o ]`.

This is the `PairPlanner.original` formula in column-vector form. The evaluator and saved diagnostic use those original-model points, with `M` above. Stage84 preparation verifies the original OBJ hash and reproduces the historical transformed vertex/face hashes, not a new alignment.

The historical comparator fit passed its declared geometry checks; reserved33-landmark pooled p90 distance was0.060505m. This is same-capture reconstruction agreement, **not** an independent physical calibration-error bound. The internal Polycam fusion frame subset/optimized poses remain unavailable. These uncertainties affect the source route and any physical interpretation; they do not turn the diagnostic into an identity assumption between raw OBJ and camera pose coordinates.

## Primary-paper support and limits

The [WACV2024 primary paper, §3.1.2 (pp.4511–4512)](https://openaccess.thecvf.com/content/WACV2024/papers/Ren_MuSHRoom_Multi-Sensor_Hybrid_Room_Dataset_for_Joint_3D_Reconstruction_and_WACV_2024_paper.pdf) describes iPhone RGB cropping and depth upscaling/alignment from native resolutions, and reference mesh post-processing that removes incorrect vertices and completes holes after triangulation. Therefore **author-cleaned/hole-completed FARO-derived reference mesh** is supported; it does not establish which particular face was repaired. The [author arXiv version, §3.1.2](https://arxiv.org/html/2311.02778v3) was directly readable in this review. Direct CVF opening returned403, although its search-index text verified the iPhone preprocessing paragraph. No paper binary or dataset frame was newly downloaded.

The photo/depth files inspected are published processed738×994 exports, not native raw buffers. UInt16×0.001 values are nominal axial metres under the reviewed export convention. Original confidence, tracking, capture timestamps and independently measured RGB-depth/pose/FARO-registration uncertainty are unavailable. Neither the paper's processing description nor selected pose equality supplies them.
