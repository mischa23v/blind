## Mac and phone sequence

1. Move the verified source archive to the M1 Mac. Follow `MAC_HANDOFF.md`. Run the base build first: `npm run mac:setup -- --ui`. An Apple compiler failure is a blocker to fix, not a passed feature. Preserve `artifacts/mac-checks` logs.
2. Install the base app on the existing iPhone with Xcode. Begin seated: verify all tabs/buttons, deny/grant permissions, cancel actions, stop monitoring and change English/Arabic/VoiceOver settings. Test the simulator fixtures before live sensors.
3. Test real phone sensing as an adult in a controlled familiar space with a helper. Use harmless fixtures and record actual measurements; never ask a child to approach an exposed drop to test an alert. Check tracking loss, covered camera, locked phone, app background, low battery and recovery.
4. Test the full offline path with network disabled. Evaluate actual local LLM availability/Arabic with `npm run evaluate:apple`, and separately on the phone. An unsupported result is a limitation to resolve; do not label fixed Arabic phrases as a conversational Arabic model.
5. Validate parent mapping, keep-out persistence and manually aligned routes. A room drawing alone does not authorize navigation. Build native RTAB-Map separately after the base build is working and sufficient storage is available.
6. Assemble a small electronics bench only after these phone checks. Then validate full hardware: disconnected/stale sensor, wrong role, dropped Bluetooth, MCU restart, broken mux branch, power sag and local alerts without the phone. Record acquisition-to-alert latency rather than relying on nominal update rates.

For each trial, record app/firmware versions, device/OS, setup and mounting, expected result, observed result, missed/late/false warnings, position error, worst measured latency, temperatures, runtime and the reviewer's decision. Avoid collecting identifiable children's videos or histories for a public demo.

## Evidence before children use walking guidance

An orientation-and-mobility specialist and an adult tester must review the intended tasks, cane use, routes and understandable alerts. Establish stopping-distance and position-error requirements for the actual setting before judging measured results. A child should not be the first person to discover whether the system detects a hazard. First validate stationary information features, then short supervised routes in a familiar controlled area. Any missed/late critical alert, misleading direction, uncertain position treated as known, confusing warning, or power/audio failure blocks expanding that trial until investigated and retested.

The professional review has not occurred and no child trials have occurred. [Perkins describes individualized orientation-and-mobility training](https://www.perkins.org/giant-steps-orientation-and-mobility/); our feature tests do not replace that instruction.

There is currently no defensible percentage chance that the whole system will work reliably for children. The evidence supports continuing engineering evaluation. It does not support a promise of independent travel, emergency evacuation or prevention of every accident. A public post may describe a prototype and invite adult feedback after the license review; publish the limitations and actual test results alongside demonstrations.
