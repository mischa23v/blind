# Explicit menu-reading aliases — bounded source increment

## What changes

Exact whole-request English and Arabic menu-reading commands select the existing captured-document adapter. English examples: `read the menu`, `read this menu`, `read menu`, `read the menu to me`, `read me the menu`. Arabic: `اقرأ قائمة الطعام`, `اقرأ لي قائمة الطعام`, `اقرأ قائمة الطعام لي`. Each English phrase also accepts the literal leading form `can you`, `can you please`, `could you`, or `could you please`. Arabic polite requests are exactly `هل يمكنك قراءة قائمة الطعام`, optionally followed by `لي`, `من فضلك`, or `لي من فضلك`. Existing bare imperative aliases retain one leading `please` or `من فضلك`; prefixes do not cascade. Trailing sentence punctuation, case/spacing and existing Arabic diacritic normalization are supported. Quoted discussion, “I wonder if…”, negation, conditionals and additional clauses do not become new menu aliases. This is a bounded set of ordinary complete polite requests, not arbitrary natural-language menu interpretation. Legacy reading commands are unchanged. Parser rejection here proves only that the new deterministic captured-document alias is not selected: pre-existing `ConversationIntent` prefix classification may still send a trusted extra-clause request such as `read the menu and order soup` to generic visual conversation. This stage does not change that fallback or claim controller-wide no-camera behavior for rejected aliases.

The existing page introduction and uncertain captured-text quotation remain unchanged. This is not menu understanding: OCR retains lines, not semantic item/column/price/qualifier relationships. No menu completeness, availability, price association, allergen safety, recommendation or real-world goal completion is inferred. No new model, dependency, persistent data or camera instruction is added.

## Route and ownership

Trusted `receiveCompanionUtterance` first offers existing captured-page review, then clears the retained page for a new request. Its change-goal authority gate precedes `routeEverydayTask`. `EverydayTaskRequest.route` reuses `ReadingToolCommand.parse` and maps `.document` to `.readDocument`; the existing coordinator ticket calls `startReadingTool(.document)`. `usesCapturedText` selects the existing captured-RGB path, which freezes one view, runs local Vision OCR and installs uncertain historical text with the existing source/request/session identity and speech budgets. Review keeps the same source and new playback ownership, not a new capture or semantic query.

Unverified microphone, model output, observed OCR and unknown origins have no change-goal authority. Text matching never establishes authority. Existing foreground, private-audio, camera, hazard and stale-result checks remain unchanged. The microphone cannot currently authorize hands-free task changes; portable tests do not establish that user experience.

## Existing repeated-request behavior, deliberately unchanged

Repeating the same exact active request retains its two-attempt coordinator budget, including pause/resume on interruption. Once the coordinator is terminal `needsHelp`, an explicit `begin` can restart its counter while retaining the parent goal; an explicit new capture after `informationReady` can also begin again. Request identity still includes the exact query: differently worded aliases remain new explicit requests under the existing coordinator contract. This is existing document behavior, not a menu-specific reset or camera/privacy permission. The alias change does not decide whether a future product contract should distinguish terminal retries from new captures. A new trusted request clears a retained source before dispatch; existing review requests intercept first. Counters and `informationReady` do not prove speech completion or real-world goal completion.
