No Jev API calls, account/key setup, installs, model downloads or image uploads were performed or authorized by this research. ## What it could establish—and what it cannot

A verifier supplied the exact same captured image can independently reassess a narrow claim. A verifier supplied only the first model's caption merely checks text against text. Neither agreement nor a valid output schema proves visual truth, and two models may share errors. Do not assume statistical independence or multiply their confidence values.

[Choice/Score confidence](https://docs.typesafe.ai/confidence) summarizes concentration of the returned probabilities; it is not a separately observed correctness rate. Noul returns a yes probability without a separate confidence. [Box documentation](https://docs.typesafe.ai/primitives/box) gives no recommended confidence threshold: it requires calibration on one's own images. A box around a door does not establish open/closed state; a chair box does not establish occupancy.

Frame-byte hash, timestamp/orientation, request/session identity and matching completion ownership establish pipeline provenance, not perceptual accuracy or proof that a model causally used the pixels. Existing [captured-text receipts](evaluations/captured-text-receipts-20261025/README.md) and [independent-observation repeat suppression](evaluations/passive-scene-delivery-20261025/README.md) already distinguish these limits. No existing Jev experiment was found in the reviewed tracker/research search.

## Bounded proposed evaluation (not executed)

1. Freeze an evaluation manifest, model/version, prompts, decoding settings and thresholds before scoring. Use the existing app/inference path where available; do not presume a bundled generic image model. Record unavailable stages rather than substituting cloud inference.
2. Prepare 24 matched local image pairs: 12 doors open/closed and 12 chairs occupied/empty, plus 12 ambiguous/occluded images. Obtain human reference labels, exact target association and visibility labels. These are a proposed pilot size, not collected fixtures or statistical reliability certification. Split by scene into development and held-out sets to prevent near-duplicate leakage.
3. Ask atomic appearance/state questions with explicit `unknown/not visible` outcomes. Keep the question fixed while swapping the matched images. Add absent-image and blank-image controls, misleading prior text, and reordered choices. Reset history between independent trials. A changed answer alone is insufficient: it must change to the correct labelled state. Blank-image failure diagnoses reliance on priors; passing it alone does not prove grounding.
4. Compare baseline, same-model recheck and a separately authorized independent verifier, if available. Give verifier the same frame and neutral atomic question before showing the generator answer to reduce anchoring. Gate or withhold unsupported ordinary descriptions rather than automatically rewriting them into new unverified claims.
5. Report wrong claims accepted, correct claims rejected, abstention/coverage, accuracy among accepted claims, matched-pair state accuracy, blank/absent-image assertions, and joint generator/verifier errors. Show per-scene counts and uncertainty intervals; do not select thresholds on held-out cases. Any correction must be rescored against human labels, including newly introduced errors.
6. Measure end-to-end capture-to-approved-answer and correction latency (median/p95/max), added verifier latency, timeout/abandonment rate, and stale-result rejection. Check interruption/camera-off/session changes; a delayed correct answer about an old frame must not become a current claim. Preserve independent hazard processing and its latency; no model/network dependency may be added there.

Stopping condition: complete the frozen pilot once, preserve every failure/unknown, report whether verification improves accepted-claim error at comparable coverage and acceptable measured latency, and make an explicit adopt/reject/more-evidence decision. Thresholds and acceptable latency need a predeclared application-specific contract before execution. No claim of actual improvement is currently supported.

## Research precedent, not an adoption

[Woodpecker's primary paper](https://arxiv.org/html/2310.16045v2) validates claims with separate object detection and VQA. On POPE random it reports MiniGPT-4 accuracy 54.67 to 85.33 percent, but LLaVA 86 to 87.67 percent with recall falling from 84 to 78.67 percent. These benchmark trade-offs motivate measuring both false acceptance and lost useful answers, not expecting universal gains. The released pipeline uses GPT-3.5, GroundingDINO and BLIP2-FlanT5-XXL; it is not a ready phone-local replacement. A permissive repository license was not verified.

## Deeper review: a silent decision layer, not a second chatbot — 2026-10-28

**The user's intended distinction is valid:** a fast machine-facing layer can evaluate many narrow conditions without composing conversational prose, while the conversational model handles the explanation. Jev should be assessed in that role, not reduced to asking another chatbot for reassurance. Example proposed checks on one frame are target visibility, door state and chair occupancy, each with an explicit unknown outcome. These checks can run before or alongside conversational generation; code decides which results are relevant and whether an ordinary visual claim is supported. This is an architectural recommendation, not an implemented background service.

### What is different from a one-word local answer?

[TypeSafe's System One description](https://docs.typesafe.ai/concepts/system-one) defines typed decisions and probabilities, rather than generated replies. Its [training primer](https://docs.typesafe.ai/introduction/machine-learning-primer) describes Reinforcement Learning for Calibrated Decisions (RLCD): post-training toward decisions whose probabilities match outcome frequencies, rather than preferred prose. Calibration describes groups of predictions, not infallibility on an individual frame; image-domain calibration remains unmeasured here. Merely requesting `yes`, `no` or one word from a generative model does not confer that training objective or calibrated probabilities.

The [launch report](https://typesafe.ai/blog/introducing-system-one-models-and-jev) describes a new architecture and parallel sampler, returning outputs together instead of autoregressive text. This is the vendor's disclosed design claim, not an independently inspected model implementation. It reports 70–500 ms end-to-end calls, mostly measured from West-Coast laptops near its service. Its prominent workflow speedups use reference probabilities from other models rather than human visual ground truth, and structured LLM probability output costs more than discrete answers. Its Doom demonstration used structured textual game state, not images. None establishes live-camera latency or phone-local performance.

A local generative model constrained to one label remains a useful **competitor to measure**, not an equivalent implementation to assume. Compare identical frames, questions and unknown handling; test discrete-label mode separately from probability-output mode. Include image encoding/prefill, decode, scheduling and any retries in latency. A one-word response can reduce decoding work but cannot remove the input/perception work, establish calibration, or guarantee equal speed/accuracy. The official MIT [System One adapter](https://github.com/typesafe-ai/system-one-adapter-python) explicitly supports both discrete and probability modes plus structured output for comparisons with LLM APIs. Its existence is not evidence that our local runtime supports it; no adapter was installed or executed.

### Evidence for many simultaneous checks

[Speculative fan-out](https://docs.typesafe.ai/patterns/fan-out) recommends grouping independent questions in one request, evaluating them in parallel and letting code discard irrelevant results. This avoids a serial chain of model round trips. Questions genuinely dependent on a previous answer still require code to resolve that dependency; speculative answers are not self-authorizing actions.

The vendor's [parallel-questions cookbook](https://docs.typesafe.ai/cookbooks/parallel_questions) supplies a concrete measured example: Jev-1.12, 13 questions against a 53,777-character text, five repetitions per strategy. The batched call averaged **0.27 seconds** versus **2.71 seconds summed across 13 serial calls**, with costs $0.000497 versus $0.006090. Concurrent individual calls would narrow that latency gap. The printed table contains two noisy questions; for one, batched/single means differ by 0.010. Treat this as a small text batching demonstration, not proof of identical answers under every workload, a current-version image benchmark, or a guarantee of sub-second response.

### Background picture/live-feed applicability and remaining evidence

Our inference: the intended design is a bounded asynchronous evidence checker over selected fresh frames, not a continuously talking model. A live feed would need frame selection, explicit capture identity, cancellation, backpressure and expiry in the app. A model completing one image request quickly is not proof of streaming-video understanding, temporal tracking, sustained frame rate or iOS background-camera operation. Sensor-derived structured state can also be checked, but correctness then depends on the sensor evidence; it cannot substitute for evaluating actual pixels when the claim is visual.

There is an official documentation inconsistency: the System One overview still says text-only, while the newer [image API page](https://docs.typesafe.ai/images) and October 14 release explicitly document experimental images. Use the newer image-specific contract; do not infer production-ready video from either. The hosted/private-image restrictions above remain unchanged.
